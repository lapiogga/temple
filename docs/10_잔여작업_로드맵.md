### 미해결 — 컨트롤 경계선 대비 (사용자 결정 필요)

경계선을 두른 컨트롤 7종이 `--n-stroke-2`(#e4e0d8) 를 쓰고 있어 WCAG 1.4.11
(컨트롤 경계 3:1)에 미달이다. 굵기가 아니라 **색** 문제다.

이 항목은 시안(`design/reference/Fluent2_구조시안.html`)의 판단선을 다시 봐야
한다. 시안은 처음에 Stroke1/Stroke2 전부를 3:1 로 걸어 실패 판정했다가 **그것을
자기 오류로 철회했다** — 1.4.11 이 장식용 구분선을 면제하기 때문이고, 근거로
Fluent 자신의 `colorNeutralStroke1`(#d1d1d1)도 흰 배경 1.53:1 이라는 점을 들었다.
그리고 예외를 **입력 필드 하나에만** 그어 `e0ffaf1` 에서 `--n-stroke-acc` 로 고쳤다.

문제는 그 선이 어디까지인지다. 시안이 입력 필드에 댄 논리("테두리가 그 컨트롤을
식별하는 요소라 면제 대상이 아니다")는 `.pg-num`(클릭 영역의 경계) ·
`.ev-radio`(선택 알약의 범위) · `.find-tab` · `.post-tabs a` 에도 그대로 적용될
여지가 있다. 반대로 `.btn-ghost` 는 글자가 16:1 로 또렷해 테두리 없이도 버튼으로
읽히므로 장식 쪽에 가깝다. 즉 7종을 한 덩어리로 볼 사안이 아닐 수 있다.

| 컨트롤 | 배경 | 현재 |
|---|---|---|
| `.btn-ghost` · `.top-admin` · `.pg-num`/`.pg-arrow` · `.post-tabs a` | 흰 서피스 | 1.32:1 |
| `.find-tab` · `.ev-radio` · `.adm-link-btn` | 한지 | 1.26:1 |

선택지 세 개. 전부 `--n-stroke-2`(#e4e0d8) 를 무엇으로 바꾸느냐의 문제다.

### `/about` — 운영에서만 깨져 있던 리다이렉트

운영이 `/about` 에 **`Location` 헤더 없는 307** 을 돌려주고 있었다. 브라우저가 따라갈

에서 PPR 과 무관하게 가져온다. PPR 이 꺼진 이 프로젝트에서는 `.next/server/app/about.meta`

### 업로드 크기 — 운영에서 1MB 에서 잘리고 있었다

nginx 에 `client_max_body_size` 가 없어 기본값 **1m** 이 걸려 있었다. 앱이 약속한
한도(이미지 8MB · 첨부 20MB)는 도달조차 못 한다.

실측: 2MB 본문이 nginx 경유 **413**, 같은 것을 `:3000` 직접으로는 통과(404 = 앱이 받음),
900KB 는 통과. dev 는 nginx 를 안 거치므로 이 벽이 안 보인다 — 실제로 2.87MB PNG 가
dev 에서는 정상 저장돼 있었다.

**Next 서버액션의 1MB 상한은 원인이 아니다.** `action-handler.js:495` 의 검사는
multipart 가 아닌 경로에만 걸리고, 파일 업로드는 busboy 의 `fieldSize`(텍스트 필드용)라
파일에는 적용되지 않는다. 병목은 nginx 하나다.

`deploy/nginx-temple.conf` 에 `client_max_body_size 128m` 을 넣었다. 값의 근거는
한 요청 최대치다 — 갤러리 일괄 8MB × 15장 = 120MB(`MAX_BATCH`), 히어로 8MB × 10장,
회원 첨부 20MB. 자르는 주체가 앱이어야 파일명과 사유가 나온다.

**운영 반영은 사람이 해야 한다**(sudo). §2-D 끝의 명령 참고.

### 타임존 — 두 종류가 섞여 있었다

서버 TZ 가 UTC 라 `created_at` 류가 **KST 00:00~09:00 에 올린 글에서 하루 앞당겨** 표시됐다.
그런데 일괄로 KST 를 걸면 안 된다는 것이 조사에서 드러났다.

- **(A) 순간** — `created_at`·`published_at`·`answered_at`. 실제로 일어난 시점이라 KST 로 표시해야 한다.
- **(B) 벽시계** — `events.starts_at`·`recurrence_until`. 관리자가 친 "2026-08-04 18:00" 을
  시간대 없는 문자열로 조립해 서버에서 `new Date()` 로 파싱하므로 **18:00+00** 으로 저장된다.
  순간이 아니라 벽시계에 UTC 라벨이 붙은 것이라, KST 로 읽으면 9시간 밀려 오전 3시가 된다.
  실측으로 확인: id=3 이 `2026-08-04T18:00Z` 인데 `when_text` 는 `"2026-08-04 18:00"`.

그래서 (A)는 KST, (B)는 **UTC 로 명시 고정**했다. 지금 서버가 UTC 라 (B)는 표시값이
바뀌지 않는다 — **기존 데이터 이전이 필요 없다.** 대신 주변 TZ 의존이 사라져,
systemd 에 `TZ` 를 넣거나 서버를 옮겨도 행사 시각이 밀리지 않는다.

포맷 로직은 12곳에 복제돼 있던 것을 `src/lib/format.js` 한 곳으로 모았다.

### nginx limit_req — 화면을 열기만 해도 잠겼다

키가 `$binary_remote_addr` 하나라 메서드를 가리지 않았다. 실측하니 **GET 7번째부터
503**(rate 5r/m + burst 5 라 6개까지 통과). 비밀번호를 한 번도 넣지 않았는데 잠기므로,
무차별 대입을 막는 게 아니라 정상 사용자를 막고 있었다. 새로고침이나 뒤로가기만으로도 걸린다.

`map $request_method` 로 키를 갈라 POST 에만 IP 를 주고 나머지에는 빈 문자열을 준다
(nginx 는 키가 비면 그 요청에 제한을 적용하지 않는다). 차단 응답도 503 → **429** 로 바꿨다 —
503 은 운영자가 서버 장애로 오인한다.

`limit_req_zone`·`map` 은 http 컨텍스트라야 해서 `deploy/nginx-temple-limit.conf` 를
새로 만들었다. 예전에는 그 내용이 `nginx-temple.conf` 주석에만 있었는데, 주석은 옮길 때
빠뜨리기 쉽고 고쳐도 이력에 안 남는다.

격리한 nginx 를 비루트 포트에 띄워 동작까지 확인했다 — GET 15번 전부 200,
POST 는 6개 통과 후 7번째부터 429, **POST 로 막힌 뒤에도 GET 은 200**.

이어서 `/member-login`·`/member-login/reset`·`/join`·`/find-account` 에도 붙였다.
이 경로들에는 nginx 제한이 **하나도 없었다.** 관리자와 zone 을 나눈 이유는 뒤에 있는
사람 수가 달라서다 — 신도 여러 명이 한 공유기(NAT) 뒤 같은 공인 IP 로 보일 수 있어,
분당 5회로 묶으면 여럿이 몰릴 때 정상 가입이 서로를 막는다. 회원용은 10r/m · burst 10.

같은 격리 환경에서 잰 결과: 회원 경로 GET 각 20번 전부 통과 · POST 는 11개 통과 후
12번째부터 429 · **회원 zone 이 소진돼도 관리자 zone 은 따로 돈다**(6개 통과 후 429) ·
정규식 location 이 `/_next/static/`·`/uploads/` 를 가로채지 않는다(429 한 번도 안 남).

(검증 중 한 번 헛짚었다. 처음엔 `return 200` 으로 테스트했는데 `return` 은 rewrite
단계라 preaccess 의 `limit_req` 보다 먼저 끝나 제한이 아예 안 걸렸다. 대조군도 같이
안 걸리는 것을 보고 알았다. 정적 파일로 바꿔 전체 단계를 태워야 한다.)

기각 11건 중 되짚어둘 것: `.sec-head-aside .back-link` 실높이 32.5px 는 반박문 스스로
"치수 계산은 지적이 맞다" 고 적었다(§2-B 에 이미 있는 항목이라 기각으로 분류됨).

## 6. 순서의 이유

- **배포 경로 복구(3-B 5) → 그 외 전부**: `deploy.sh` 가 죽어 재배포 표준 경로가 없다.
  prod 가 뒤처졌던 것도, 2026-07-29 수정을 수동 4줄로 때운 것도 그래서다.
- **업로드 경로 정비(10) + 이미지 최적화(11) → 콘텐츠 이관**: 이관 후에 고치면 2000장을 다시 처리해야 한다.
  특히 소식 커버 검증은 이관 데이터에 `/uploads/` 를 넣는 순간 **수정 저장 전면 차단** 회귀를 만든다.
- **개인정보방침(7) + 본인인증 결정 → 정식 오픈**: `/join` 이 이미 실데이터를 수집한다.
  도메인·certbot 보다 이쪽이 실질 게이트다.
- **도메인 → certbot → 카카오키 재빌드 → noindex 해제 → HSTS**: 순서를 바꾸면
  브라우저 경고가 뜨는 IP 사이트가 색인되거나 도달 불가 URL 이 OG 에 굳는다.
- **Node 22 전환은 재빌드를 동반**하므로 3-C 코드 작업과 묶으면 빌드 1회로 끝난다.
